# Porting AFFiNE, Outline, and Docmost to Cloudflare Workers: A Code-Grounded Feasibility Analysis

## TL;DR
- **None of the three ports cleanly to Cloudflare Workers as-is; all three are long-lived Node.js server processes (NestJS/Koa) that assume TCP sockets, Redis-backed blocking queues, and persistent WebSocket servers — Docmost is the least-bad port target, Outline is second, and AFFiNE is effectively impossible to port because its backend loads a napi-rs Rust `.node` native addon (`@affine/server-native`) at runtime, which V8 isolates cannot execute.**
- **The pragmatic answer is a hybrid, not a full port: put the stateful Node backend (NestJS/Koa + Hocuspocus/Socket.IO + BullMQ) on a Cloudflare Container / Fly.io / Railway VM, use Hyperdrive→managed Postgres, R2 for blobs, and only push the frontend SPA and optionally a Durable-Objects-based realtime layer to the edge. A true "fully Cloudflare-native" (D1/DO/R2/Queues-only) deployment requires a rewrite, not a port.**
- **If real-time collaborative editing is the core requirement, the highest-leverage option is to build a purpose-built edge-native app: Hono + Durable Objects (WebSocket Hibernation) + y-durableobjects/PartyServer for Yjs sync + D1/Hyperdrive + R2, reusing only the editor layer (Tiptap/BlockNote/BlockSuite). This is likely comparable in effort to a serious port of Outline or AFFiNE and yields a far better result.**

## Key Findings

**AFFiNE (github.com/toeverything/AFFiNE) — not portable.** The backend package `@affine/server` is a NestJS 11 application whose `packages/backend/server/src/native.ts` does `require('../server-native.node')` at load time. That native module, `@affine/server-native` (built from `packages/backend/native` via `@napi-rs/cli`), compiles Rust crates — including the `y-octo` CRDT engine, `affine_common` document parsers, and `tiktoken-rs` — to a platform-specific `.node` binary. The server calls into it at runtime for CRDT merges (`applyUpdatesWithNative` in `core/doc/storage/doc.ts`; `adapter.diff(...)` using y-octo in `core/sync/gateway.ts`). Cloudflare Workers run V8 isolates and cannot load native `.node` addons, so this is a hard blocker independent of everything else. On top of that: Prisma 6.6.0 against PostgreSQL, `socket.io` 4.8.1 (long-lived WS server with a Redis adapter), `bullmq` + `ioredis` background workers, `nodemailer`, and `@aws-sdk/client-s3`.

**Outline (github.com/outline/outline) — portable only as a hybrid; blocked from full-edge by Sequelize + Bull + Passport + Koa long-lived process.** Outline is a single Koa monolith (`koa` ^3.0.3) whose services (`web`, `websockets`, `worker`, `collaboration`, `cron`, `admin`) are toggled by the `SERVICES` env var but run in one Node process via `throng`. Data layer is Sequelize 6 over `pg` (raw TCP Postgres, connection pooling, read replicas), which fundamentally assumes a long-lived pooled TCP connection — incompatible with the per-request isolate model. Realtime is split: a Socket.IO layer (`socket.io` + `socket.io-redis`) for presence/notifications and a Hocuspocus 1.1.3 (`@hocuspocus/server`) Yjs collaboration server. Background jobs use Bull 4 (`bull`) + `ioredis` (blocking Redis). Auth is Passport (`@outlinewiki/koa-passport`). Full-text search uses Postgres `tsvector`/`pg-tsquery`. The frontend is a Vite React SPA that can trivially go to Cloudflare Pages/Static Assets.

**Docmost (github.com/docmost/docmost) — the best port target, but still not fully edge-native without a data-layer rewrite.** Docmost server (`apps/server`) is NestJS 11 on the Fastify adapter, using Kysely (query builder, not a heavy ORM) over PostgreSQL via `pg`, BullMQ 5 + ioredis for queues, Socket.IO 4 with a Redis adapter, and Hocuspocus 4.5.0 + Yjs for collaboration (run as a *separate* deployable process, `collab-main.js`, on port 3001). Storage is a clean driver abstraction (`LocalDriver`/`S3Driver`) selected by `STORAGE_DRIVER`. **Critical blocker for image handling: Docmost uses `sharp` (native libvips binary) in `compressAndResizeIcon()` to compress/resize avatars and icons — not Workers-compatible.** Full-text search is Postgres-based. Auth is JWT via `@nestjs/jwt` + Passport. Kysely is the one architectural advantage: it can target a Workers-compatible Postgres driver, so the data layer is the most portable of the three.

## Details

### 1. Runtime compatibility with workerd

Cloudflare Workers provide a subset of Node.js APIs behind the `nodejs_compat` flag (which also enables `nodejs_compat_v2` for compatibility dates ≥ 2024-09-23). Natively supported now include `assert`, `buffer`, `crypto`, `stream`, `path`, `util`, `events`, `async_hooks`/`AsyncLocalStorage`, plus (added 2025-01-28) `node:net` (client `net.Socket` and `net.BlockList` — but **`net.Server` is not supported**), `node:dns` (over DoH), and `node:timers`. `node:http` client and server were reimplemented on top of `fetch()` in 2025, which is what lets Express/Koa-style apps *bootstrap* at all. `child_process`, `worker_threads`, and arbitrary `dgram`/raw server sockets remain unavailable or stubbed.

Hard limits that matter here (all confirmed verbatim against Cloudflare's official Workers limits doc):
- **Memory: 128 MB per isolate** on both Free and Paid — the table reads "Memory | 128 MB | 128 MB," and this cap cannot be raised by upgrading your plan. It is a runtime heap ceiling, not just bundle.
- **Bundle size: 3 MB (Free) / 10 MB (Paid)** compressed worker script ("Worker size | 3 MB | 10 MB"). Each Durable Object class registered adds baseline memory to the isolate.
- **CPU time: 10 ms (Free) / 30 s default, up to 5 min (Paid)** per request ("CPU time per HTTP request | 10 ms | 5 min (default: 30 seconds)"; the `cpu_ms` value is opt-in-configurable up to 300,000 ms). This is CPU, not wall-clock — I/O waits don't count.
- **6 simultaneous outgoing connections per invocation** ("Simultaneous outgoing connections/request | 6 | 6") — a Worker cannot hold a big connection pool.

**Native binary blockers (decisive):**
- AFFiNE: `@affine/server-native` (napi-rs `.node`) — cannot load. Full stop.
- Docmost: `sharp` (libvips native) — cannot load; used for avatar/icon resize. Would need to be replaced (Cloudflare Images/Image Resizing, an external service, or drop server-side resize).
- Outline: no napi-rs backend, but `@aws-sdk/signature-v4-crt` pulls an AWS CRT native binding, `jsdom` and `mammoth`/`mailparser` are heavy, and `bull`/`ioredis` assume raw Redis TCP.

### 2. Framework compatibility

**NestJS does not run on Cloudflare Workers in any supported way.** It assumes a long-lived HTTP server (`app.listen()`), heavy DI graph construction per process using `reflect-metadata`/`emitDecoratorMetadata`, module lifecycle hooks (`onModuleInit`, `onModuleDestroy`), and platform adapters (Express/Fastify) that expect a persistent server. Community consensus and Cloudflare's own forums confirm NestJS is unsupported on Workers; people who "deploy NestJS to Cloudflare" are using Cloudflare **Containers**, not the isolate runtime. Per-isolate cold-start of the entire Nest DI container would also blow the 1-second startup budget and inflate memory. This applies to **both AFFiNE and Docmost**.

**Koa (Outline)** is closer: with `node:http` now emulated on `fetch()`, a Koa app can theoretically boot. But Outline's Koa app is a *long-lived multi-service process* (`throng` cluster, `stoppable` graceful shutdown, mounted Socket.IO server, Bull workers, Hocuspocus server) — the server *shape*, not just the HTTP layer, is the problem.

### 3. Database layer

- **Prisma (AFFiNE):** Prisma can run on Workers via driver adapters + Hyperdrive or Prisma Accelerate, but this is moot for AFFiNE given the native-addon blocker.
- **Sequelize (Outline):** Sequelize 6 over `pg` needs a persistent pooled TCP connection and does connection lifecycle management incompatible with per-request isolates. There is no first-class Workers dialect. Even over Hyperdrive (which does give Workers TCP-to-Postgres via `pg`), Sequelize's pool assumptions and migration tooling (`sequelize-cli`, `umzug`) fight the model. This is the single biggest data-layer obstacle for Outline.
- **Kysely (Docmost):** Kysely is the friendliest — it's a thin query builder and can be pointed at a Workers-compatible Postgres driver. Over **Hyperdrive**, `pg` (node-postgres, ≥ 8.16.3) and `postgres.js` both work, with the caveat that you construct a fresh client per request (Hyperdrive maintains the real pool close to the DB, operating in transaction mode) and close it via `ctx.waitUntil()`. Note the 6-connection-per-invocation ceiling means any local pool should be kept ≤ 5. Alternatively the Neon serverless driver (WebSocket/HTTP) works without Hyperdrive.
- **Fully-native (D1) scenario:** D1 is SQLite, capped at **10 GB per database on Workers Paid (500 MB on Free)**, processing queries sequentially on a single thread. It lacks the Postgres extensions all three projects rely on — `tsvector`/`pg_trgm` full-text search (Outline, Docmost), `JSONB` semantics, `pgvector` (AFFiNE embeddings), `ltree`. Porting to D1 means rewriting search (to SQLite FTS5), rewriting all JSONB/array queries, and re-modeling migrations. This is a rewrite of the persistence layer, not a config change. **Divergence:** in the "Workers + external managed Postgres via Hyperdrive" scenario the schema/queries survive largely intact (Kysely/Sequelize SQL still runs on real Postgres); in the "fully Cloudflare-native/D1" scenario they do not.

### 4. Realtime collaboration / CRDT sync (the hardest part)

All three ultimately move Yjs updates; the transport differs. Cloudflare's idiomatic answer is a **Durable Object per document** holding the authoritative Y.Doc, accepting WebSockets via the **Hibernation API** (`this.ctx.acceptWebSocket(server)`), which keeps clients connected while the DO is evicted from memory (no duration billing while idle) and re-runs the constructor on the next message. State that must survive hibernation is persisted via DO Storage (KV or SQLite) and/or serialized to R2 using `serializeAttachment`/`deserializeAttachment` for per-connection metadata.

- **Hocuspocus (Outline, Docmost):** Historically Hocuspocus depended on the `ws` package and Node, so it could not run on Workers. **Hocuspocus v4 (released 2025) switched to `crossws` and is MIT-licensed and explicitly advertised to run on Cloudflare Workers** — its release notes state "Cross-runtime WebSocket support via crossws — Bun, Deno, Cloudflare Workers, Node/uWebSockets all supported," and the maintainer confirmed it is "no longer tied to Node." Docmost is already on `@hocuspocus/server` 4.5.0; Outline is pinned to Hocuspocus **1.1.3**, which is Node-only. So Docmost's collaboration server is, in principle, the closest to running at the edge — but Hocuspocus still expects to be the persistent server holding docs, so mapping it into the DO lifecycle (one DO per document, persistence hooks writing to R2/D1) is non-trivial integration work even on v4.
- **AFFiNE:** sync is Socket.IO + y-octo (native Rust) + Redis pub/sub + Postgres. The CRDT merge itself runs in the `.node` addon. Porting means replacing y-octo-native with JS Yjs inside a DO — a reimplementation, not a port.
- **Ready-made building blocks:** `y-durableobjects` (napolab) implements Yjs-over-Durable-Objects with Hibernation and Hono, "eliminating Node.js dependencies," persisting updates to DO storage; `PartyServer`/PartyKit (now a Cloudflare project) with its Yjs base class; `y-sweet` (Rust, deploys as WASM on Cloudflare's edge, persists to S3-compatible storage); and Cloudflare's own edge-chat-demo. `TimoWilhelm/yjs-cf-ws-provider` is a reference Yjs WS connector on Workers+DO using Hibernation and periodic R2 snapshots. **Caveat:** every WebSocket message counts as a billable request, which for high-frequency CRDT sync can get expensive.
- **If you drop realtime collab:** the port simplifies enormously. Without Hocuspocus/Socket.IO/Yjs you can serve documents as request/response REST over Workers+Hyperdrive+R2, and Durable Objects become optional. For a "Notion-like" product this is usually unacceptable, but it's the single biggest scope lever.

### 5. Background jobs / queues

**Bull/Bee-Queue (Outline) and BullMQ (Docmost, AFFiNE) cannot run on Workers.** They rely on Redis blocking commands (`BRPOPLPUSH`/`BZPOPMIN`) and long-lived worker connections that hold a socket open and loop — there is no long-lived process on Workers, and `ioredis` needs raw Redis TCP. The Workers-native replacements are **Cloudflare Queues** (consumers get up to **15 minutes wall time** and 30 s CPU default, configurable to 5 min), **Workflows** (durable multi-step, up to 5 min CPU/step), **Cron Triggers** (scheduled; same 15-min ceiling), and **Durable Object Alarms** (per-entity scheduling). If you must keep Redis semantics, **Upstash Redis REST** works over HTTP from Workers (unlike raw `ioredis`), but it does not give you Bull's blocking-queue worker model — you'd still re-architect the job consumers. Every job type (email send, exports, embeddings, notifications, snapshotting) has to be re-expressed as a Queue consumer or Workflow.

### 6. File storage & media processing

S3 → R2 is the easy win: R2 is S3-API-compatible, so `@aws-sdk/client-s3` works (ideally via the R2 binding), and presigned URLs port. Docmost's `S3Driver`/`LocalDriver` abstraction means only the driver needs a small R2 variant (and the `LocalDriver`, which writes to disk via `fs`, must be dropped). **Media processing is the blocker:** Docmost's `sharp` and any libvips/`canvas` usage won't run; you'd move image resize to Cloudflare Images or an external service, or drop it. Outline's import/export pipeline pulls in `mammoth` (docx→html), `jsdom`, `yauzl`/`yazl` (zip), `mailparser`, and `@css-inline/css-inline-wasm`; the WASM one is fine, but `jsdom` is heavy and may exceed the 128 MB / 10 MB limits. Any pandoc/ffmpeg-class native tools are impossible on Workers and must live in a container.

### 7. Search

Outline and Docmost both use PostgreSQL full-text search (`tsvector`, `pg-tsquery` in Outline). Over Hyperdrive→Postgres this **survives unchanged**. Under a D1-only target it does **not** — you'd rewrite to SQLite FTS5 (different ranking, no `pg_trgm` fuzzy matching) or bolt on an external search service. This is another reason the Hyperdrive+managed-Postgres scenario is dramatically less work than fully-native.

### 8. Auth/session

Outline uses Passport (`@outlinewiki/koa-passport`) with OAuth strategies (Google, Slack, Azure, generic OAuth2) plus `@node-oauth/oauth2-server` and WebAuthn (`@simplewebauthn/server`). Passport is middleware-based and Node-oriented; the strategies mostly do HTTP calls (portable) but the session/cookie plumbing assumes Koa middleware. Docmost is JWT-based (`@nestjs/jwt`) with Passport strategies; JWT verification is stateless and Workers-friendly (`jsonwebtoken` or WebCrypto). OIDC/SAML enterprise flows in Docmost live in the EE (commercial) directories. Net: Docmost's stateless JWT model ports more easily than Outline's Passport-session model.

### 9. Frontend/SSR

This is the uniformly easy part. **All three frontends are Vite React SPAs** (Outline: Vite + React 17; Docmost: Vite + React 19 + Mantine + Tiptap 3; AFFiNE: Rspack + React 19 + BlockSuite). A static SPA build deploys to **Cloudflare Pages / Workers Static Assets** trivially regardless of what happens to the backend. So even in the worst case (backend stays on a VM), the frontend and CDN layer can live on Cloudflare and talk to a container-hosted API.

## Recommendation

** build edge-native, reuse only the editor.** Stand up **Hono + Durable Objects (Hibernation) + y-durableobjects/PartyServer + Hyperdrive→Postgres (or D1) + R2 + Queues**, and drop in **Tiptap, BlockNote (Notion-style, collab built-in, MIT), or BlockSuite (MIT, from AFFiNE)** as the editor. You inherit none of the porting friction, none of the AGPL/BSL/EE constraints (all three editors are permissively licensed), and you get an architecture that actually fits the platform. Realistic effort: **~2–4 engineer-months** to a solid MVP with realtime collab — competitive with a *serious* port of Outline and cheaper than a full-native port of either NestJS app. There is prior art: several open-source Tiptap/BlockNote-on-Cloudflare (Hono + D1 + DO + R2) note-taking/wiki apps already exist, and Cloudflare/PartyKit ship templates for Yjs-on-DO; adopting one as a skeleton would cut the MVP timeline further.

## Comparative Verdict (ranked by porting feasibility)

**Which subsystems can stay on a container/VM in a hybrid?** The NestJS/Koa HTTP API, the Hocuspocus/Socket.IO realtime server, the BullMQ/Bull worker fleet, `sharp`/`jsdom`/`mammoth` media and import pipelines, and Sequelize/Prisma migration tooling should all stay on a Cloudflare Container / Fly.io / Railway VM. What moves cleanly to Cloudflare: the SPA (Pages/Static Assets), blob storage (R2), CDN/routing (a thin Worker), and — as a targeted upgrade — the per-document Yjs sync layer (Durable Objects). **A hybrid is the pragmatic answer for all three; a full edge-native deployment is only worth it as a greenfield rebuild.**

## Caveats
- Exact dependency version strings for AFFiNE's backend and Docmost's `apps/server` were partly corroborated via DeepWiki's code index (which cites specific file/line references) plus a targeted deep-dive on AFFiNE's native module, rather than fetched line-for-line for every entry (GitHub raw URLs were intermittently unfetchable). Majors and the presence of each dependency are high-confidence; patch versions may have drifted on `canary`/`main`. Outline's and Docmost's root `package.json` were read verbatim, as was the AFFiNE monorepo root.
- Cloudflare's Node.js compatibility surface is expanding rapidly (e.g. `node:http` server support landed in 2025; `child_process`/`perf_hooks`/`readline` stubs auto-enable on compat dates ≥ 2026-03-17). Specific "unsupported" claims should be re-checked against the live compatibility matrix at deploy time.
- Hocuspocus v4's "runs on Cloudflare Workers" claim (via crossws) is real but does not mean "drop-in into a Durable Object" — mapping the persistent-server model onto per-document DO lifecycle and storage is still design-and-integration work.
- "WebSocket message = billable request" on Workers/DO can dominate cost for chatty CRDT sync; model this before committing to edge-native realtime.
- Nothing here is legal advice; validate the AGPL/BSL/EE obligations with counsel before commercializing any fork.
