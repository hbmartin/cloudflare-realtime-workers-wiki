# Notion API compatibility: blockers and quick wins

This document compares the Notion public API (pinned at `Notion-Version: 2026-03-11`, well past the September 2025 database/data-source split — Views, Markdown, Move Page, and Templates all shipped since) against this repository's actual data model and worker routes. It exists to answer one question before anyone attempts a Notion-API-shaped integration layer on top of this app: what specifically stops that layer from moving significant ground, and what's already sitting there for the taking.

Fourteen Notion resource areas were surveyed. Four came back "ready now" — thin wrappers over data that already exists, no schema change, no new auth. The other ten trace back almost entirely to four recurring architectural gaps, not ten unrelated problems. Fix — or knowingly accept — those four, and most of the remaining surface area becomes tractable.

## The four recurring blockers

### 1. One workspace, hardcoded

Notion's entire integration model assumes plurality: a connection (internal token, PAT, or OAuth app) is scoped to one workspace among potentially many, a user can belong to several workspaces, and OAuth's install flow has an explicit "select workspace(s)" step. This app has none of that scaffolding, and not by omission — by constraint.

`install_state` carries a SQLite `CHECK (id = 1)` (`migrations/0001_initial.sql:53-57`), physically preventing a second row from ever existing. It stores exactly one `workspace_id`, and `POST /api/install/bootstrap` (`src/worker/index.ts:209-254`) is the only code path that creates a `workspaces` row — it 409s with `already_initialized` if bootstrap has already run. `getMember()` (`src/worker/auth.ts:19-49`) resolves a session to workspace membership via `SELECT ... LIMIT 1` with **no `workspace_id` filter at all** — it silently picks an arbitrary single membership row per user. There is no route anywhere in the worker or the client that lists workspaces, creates a second one, or lets a caller specify which workspace an operation targets; every route derives its scope from `member.workspace.id`, i.e. the one membership `getMember()` already resolved.

This is the right call for a self-hosted, single-tenant wiki — it's explicitly one of the [accepted v1 limits](README.md#accepted-v1-limits). It's also fine as-is for an API surface modeled on Notion's _internal integration_ concept (a static token scoped to "this workspace," which is the only workspace that exists). It only becomes a blocker the moment the target shifts toward Notion's actual multi-tenant model: an OAuth app installable across many workspaces, or a token that needs to declare _which_ workspace it's acting in because there's more than one to choose from. Removing this blocker for real is a schema and auth-flow change (drop the `CHECK`, thread `workspace_id` through `getMember()` and every route that currently assumes it), not just a config flag — and it's worth asking whether the product wants that at all before building it.

### 2. Document content lives only inside a live Yjs CRDT

This is the blocker with the widest blast radius — it's the reason Blocks, Comments, and the Markdown API are all "significant new work" rather than three separate problems.

Document body content is a single Yjs `XmlFragment` named `"document-store"`, living inside a per-page-epoch Durable Object (`src/worker/document.ts:479`, mirrored client-side via BlockNote's `withCollaboration` in `src/client/EditorPage.tsx:463-483`). Comments live alongside it in a `Y.Map("comments")` on the same document (`EditorPage.tsx:460`). D1 never receives structured content — only a lossy derived projection. `projectDocument()` (`src/shared/document-projection.ts:37-81`) walks the ProseMirror JSON and produces exactly three things: a flattened `plainText` string (capped at 500,000 characters), a list of page-mention targets, and a list of user-mention targets. Headings, lists, tables, code blocks — everything collapses into one plain-text blob. That projection only runs during debounced compaction (`Document.compactOnce()`, `document.ts:465-700`, roughly 30 seconds after the last edit), not per keystroke, so even the text that does survive lags live edits.

The only way to get bytes out of a document server-side today is `GET /api/versions/:id`, which returns a raw Yjs snapshot as `application/vnd.yjs` — opaque outside a client that links `yjs` and decodes it (`index.ts:1018-1044`). There is no REST route that reads or writes document content as JSON, at all; every content mutation happens exclusively over the authenticated WebSocket at `/parties/document/:pageId~:epoch`.

Notion's Blocks API assumes the opposite: every block is an individually addressable server-side object with a stable ID, a type, and a JSON representation reachable outside any live editing session, and mutations (`PATCH /v1/blocks/{id}`, `PATCH .../children`) are ordinary request/response writes. Closing this gap in two halves:

- **Read** is reachable without new architecture. The worker already decodes the Yjs doc to ProseMirror JSON via `yXmlFragmentToProsemirrorJSON` (`document.ts:479`) — the missing piece is doing that decode on demand for a REST read, assigning/preserving stable block IDs, and mapping BlockNote's block schema onto an enumerable type list.
- **Write** is real distributed-systems work. A REST-triggered block edit has to become a Yjs transaction applied to the document's Durable Object — which may be hibernating — not a byte overwrite, and it has to reconcile with the existing 30-second compaction cycle and the 16 MiB warning / 24 MiB read-only size ceiling (`document.ts`, `WARN_BYTES`/`READ_ONLY_BYTES`) so a REST write can't silently push a document past limits the live editor already enforces.

Comments inherit this same blocker and add one more: they use BlockNote's own `YjsThreadStore` format, which isn't a documented, stable schema independent of the BlockNote version in use, and the worker currently has zero awareness that comments exist — they never touch D1, are absent from the FTS/search projection, and have no REST endpoint of any kind. The Markdown API is a parallel content channel to Blocks and depends on the same underlying decode work; once server-side JSON block access exists, ProseMirror-JSON-to-Markdown serialization itself is a solved problem with existing libraries.

### 3. Auth is a browser session cookie, full stop

Notion offers three integration types — a static internal-integration token, a user-scoped Personal Access Token, and a full OAuth 2.0 public-integration flow — plus per-connection capability scoping (read/insert/update content; read/insert comments; three levels of user-info access) and per-page sharing grants that are independent of any global role.

This app has exactly one authentication path. `createAuth()` (`src/worker/auth.ts:7-16`) configures Better Auth with `emailAndPassword` only — no OAuth providers, no magic links, no passkeys. Every request is authorized by a session cookie, and `assertSameOrigin` (`src/worker/http.ts`) actively rejects requests whose `Origin` header doesn't match `BETTER_AUTH_URL`, which is correct for a browser-only app but would reject any external script or integration by design. Authorization itself is coarse: three global roles (`owner`/`editor`/`viewer`, enforced by `requireOwner`/`requireEditor`/`requireMember` in `auth.ts:51-67`) with no concept of a resource-scoped grant — there's no way to say "this connection can see page X but not page Y," which is exactly how Notion integrations work by default. Internal worker-to-Durable-Object calls don't have their own credential model either — they share one static secret, `x-notes-internal: env.BETTER_AUTH_SECRET`, checked identically everywhere it's used (`document.ts:351`, `workspace-events.ts:112`, `archive.ts:63`, `cleanup.ts:42`).

The closest reachable target is a bearer-token Personal Access Token, and there's already a pattern to copy: invites are hashed, single-use, expiring tokens (`token_hash`, 7-day expiry, atomic single-use consumption via `UPDATE ... WHERE used_at IS NULL` — `index.ts:256-354`, schema at `migrations/0001_initial.sql:94-104`). A PAT table following that same shape, plus a new auth middleware branch that accepts `Authorization: Bearer <token>` as an alternative to the session cookie (and a carve-out in `assertSameOrigin` for that path), is incremental work on an existing pattern. Full OAuth — an authorization server, a page-picker consent screen, refresh-token rotation, and capability enforcement layered _under_ the existing role checks — is a genuinely new subsystem, and per-page resource grants would need a new table and a new authorization check inserted into every route, since today every check just asks "what's this user's global role."

### 4. Nothing leaves the building

Notion's webhook system lets an external service subscribe to workspace events (page/database/data-source/comment/view created, updated, moved, deleted, and more), delivered as signed HTTP POSTs to a URL the subscriber controls, with a one-time verification-token handshake and HMAC-SHA256 request signing.

This app has no outbound HTTP delivery mechanism anywhere — no Cloudflare Queues binding, no webhook subscription table, no signing code, nothing (confirmed against the full binding list in `wrangler.jsonc:14-38` and `src/worker/env.ts:6-16`: only `DB`, `BUCKET`, and the two Durable Object namespaces). What it does have is a well-built _internal_ precedent that's easy to mistake for a head start until you look closely at where it stops: the `WorkspaceEvents` Durable Object (`src/worker/workspace-events.ts`) validates and fans out strictly-typed events — `pages-upserted`, `pages-removed`, `projection-updated` — every time a page mutates (`sendWorkspaceEvent`, `index.ts:87-97`) or a document finishes compacting (`document.ts:658-665`). `broadcastWorkspaceEvent()` (`workspace-events.ts:134-144`) is genuinely solid pub/sub — but it only reaches WebSocket-connected browser tabs in that workspace. It cannot POST to an external URL, has no subscriber list beyond "whoever's currently connected," and the DO itself is explicitly read-only from the client's side (`isReadOnly()` always returns `true`, line 85-87) by design, since it exists purely to push, not to accept writes.

Turning this into real webhooks means building, from nothing: a subscription table (URL, secret, event-type filter, active/paused status), a delivery mechanism (most naturally Cloudflare Queues, which isn't a binding in this project today) with retry/backoff for failed deliveries, and HMAC signing on the outbound payload. The one thing that _doesn't_ need reinventing is the event taxonomy — `WorkspaceEvent`'s existing shape (`src/shared/types.ts`) is already a reasonable starting vocabulary to extend outward instead of designing from scratch.

## Follow-up: the four areas that need none of this

These don't touch any of the four blockers above. Each is a thin translation layer over a route or index that already exists, callable today by whatever auth mechanism ends up fronting a new API surface.

**Search API** (`POST /v1/search` in Notion's shape). `GET /api/search` (`index.ts:722-738`) already queries the `page_search` FTS5 virtual table (`migrations/0001_initial.sql:128-134`), ranks by `bm25()`, and returns highlighted snippets — and it matches on **title and body text**, where Notion's own search API only matches page/data-source titles. A wrapper here is strictly a narrowing of what's already exposed, not a climb.

**Users API** (`GET /v1/users`, `/v1/users/{id}`, `/v1/users/me`). `GET /api/members` (`index.ts:326-336`) and `GET /api/me` (`index.ts:311-319`) already cover list/retrieve/current-user. The only cosmetic gap is Notion's `person`/`bot` user-type distinction — trivially satisfied with a hardcoded `type: "person"` until a PAT or OAuth identity (blocker #3) gives a token its own bot-user identity to report.

**Move Page** (`POST /v1/pages/{id}/move`). `POST /api/pages/:id/move` (`index.ts:478-523`) already does this, and does slightly more than Notion's version: it accepts a target parent plus `beforeId`/`afterId` siblings and computes a new fractional-index position in the same call, with cycle prevention via a recursive CTE (`index.ts:486-494`) rather than requiring a separate reorder step.

**Pagination and error envelope.** Notion's list responses (`{object: "list", results, has_more, next_cursor}`) and error objects (`{object: "error", status, code, message}`) both have direct analogues already in production here. Cursor pagination exists today in the mention inbox — an opaque `{firstSeenAt, pageId}` cursor with a `nextCursor` in the response (`index.ts:821-867`). The typed error model (`HttpError` in `http.ts`, with specific per-domain codes like `table_lease_lost`, `page_cycle`, and `archive_first`) is structurally the same idea as Notion's own per-domain codes (e.g. `select_required`). Standardizing on Notion's exact envelope shape, and a `Notion-Version`-style required header, for any new API surface is a naming exercise, not new engineering.
