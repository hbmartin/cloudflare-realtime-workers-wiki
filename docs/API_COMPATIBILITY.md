# Notion API compatibility: blockers and quick wins

This document compares the Notion public API (pinned at `Notion-Version: 2026-03-11`, well past the September 2025 database/data-source split — Views, Markdown, Move Page, and Templates all shipped since) against this repository's actual data model and worker routes. It exists to answer one question before anyone attempts a Notion-API-shaped integration layer on top of this app: what specifically stops that layer from moving significant ground, and what's already sitting there for the taking.

Fourteen Notion resource areas were surveyed. Three came back "ready now" — thin wrappers over data that already exists, no schema change, no new auth — and one has a narrow but explicit compatibility limit. The other ten trace back almost entirely to four recurring architectural gaps, not ten unrelated problems. Fix — or knowingly accept — those four, and most of the remaining surface area becomes tractable.

## The four recurring blockers

### 1. One workspace, hardcoded

Notion's entire integration model assumes plurality: a connection (internal token, PAT, or OAuth app) is scoped to one workspace among potentially many, a user can belong to several workspaces, and OAuth's install flow has an explicit "select workspace(s)" step. This app has none of that scaffolding, and not by omission — by constraint.

`install_state` carries a SQLite `CHECK (id = 1)` in `migrations/0001_initial.sql`, physically preventing a second row from ever existing. It stores exactly one `workspace_id`, and the `POST /api/install/bootstrap` handler in `src/worker/index.ts` is the only code path that creates a `workspaces` row — it 409s with `already_initialized` if bootstrap has already run. `getMember()` in `src/worker/auth.ts` resolves a session to workspace membership via `SELECT ... LIMIT 1` with **no `workspace_id` filter at all** — it silently picks an arbitrary single membership row per user. There is no route anywhere in the worker or the client that lists workspaces, creates a second one, or lets a caller specify which workspace an operation targets; every route derives its scope from `member.workspace.id`, i.e. the one membership `getMember()` already resolved.

This is the right call for a self-hosted, single-tenant wiki — it's explicitly one of the [accepted v1 limits](../README.md#accepted-v1-limits). It's also fine as-is for an API surface modeled on Notion's _internal integration_ concept (a static token scoped to "this workspace," which is the only workspace that exists). It only becomes a blocker the moment the target shifts toward Notion's actual multi-tenant model: an OAuth app installable across many workspaces, or a token that needs to declare _which_ workspace it's acting in because there's more than one to choose from. Removing this blocker for real is a schema and auth-flow change (drop the `CHECK`, thread `workspace_id` through `getMember()` and every route that currently assumes it), not just a config flag — and it's worth asking whether the product wants that at all before building it.

### 2. Document content lives only inside a live Yjs CRDT

This is the blocker with the widest blast radius — it's the reason Blocks, Comments, and the Markdown API are all "significant new work" rather than three separate problems.

Document body content is a single Yjs `XmlFragment` named `"document-store"`, living inside the per-page-epoch Durable Object in `src/worker/document.ts` and mirrored client-side via BlockNote's `withCollaboration` in `src/client/EditorPage.tsx`. Comments live alongside it in a `Y.Map("comments")` on the same document. D1 never receives structured content — only a lossy derived projection. `projectDocument()` in `src/shared/document-projection.ts` walks the ProseMirror JSON and produces exactly three things: a flattened `plainText` string (capped at 500,000 characters), a list of page-mention targets, and a list of user-mention targets. Headings, lists, tables, code blocks — everything collapses into one plain-text blob. That projection only runs during debounced `Document.compactOnce()` processing, roughly 30 seconds after the last edit, not per keystroke, so even the text that does survive lags live edits.

The only way to get bytes out of a document server-side today is `GET /api/versions/:id` in `src/worker/index.ts`, which returns a raw Yjs snapshot as `application/vnd.yjs` — opaque outside a client that links `yjs` and decodes it. There is no REST route that reads or writes document content as JSON, at all; every content mutation happens exclusively over the authenticated WebSocket at `/parties/document/:pageId~:epoch`.

Notion's Blocks API assumes the opposite: every block is an individually addressable server-side object with a stable ID, a type, and a JSON representation reachable outside any live editing session, and mutations (`PATCH /v1/blocks/{id}`, `PATCH .../children`) are ordinary request/response writes. Closing this gap in two halves:

- **Read** is reachable without new architecture. The worker already decodes the Yjs doc to ProseMirror JSON via `yXmlFragmentToProsemirrorJSON` in `src/worker/document.ts` — the missing piece is doing that decode on demand for a REST read, assigning/preserving stable block IDs, and mapping BlockNote's block schema onto an enumerable type list.
- **Write** is real distributed-systems work. A REST-triggered block edit has to become a Yjs transaction applied to the document's Durable Object — which may be hibernating — not a byte overwrite, and it has to reconcile with the existing 30-second compaction cycle and the 16 MiB warning / 24 MiB read-only size ceiling (`document.ts`, `WARN_BYTES`/`READ_ONLY_BYTES`) so a REST write can't silently push a document past limits the live editor already enforces.

Comments inherit this same blocker and add one more: they use BlockNote's own `YjsThreadStore` format, which isn't a documented, stable schema independent of the BlockNote version in use, and the worker currently has zero awareness that comments exist — they never touch D1, are absent from the FTS/search projection, and have no REST endpoint of any kind. The Markdown API is a parallel content channel to Blocks and depends on the same underlying decode work; once server-side JSON block access exists, ProseMirror-JSON-to-Markdown serialization itself is a solved problem with existing libraries.

### 3. Auth is a browser session cookie, full stop

Notion offers three integration types — a static internal-integration token, a user-scoped Personal Access Token, and a full OAuth 2.0 public-integration flow — plus per-connection capability scoping (read/insert/update content; read/insert comments; three levels of user-info access) and per-page sharing grants that are independent of any global role.

This app has exactly one authentication path. `createAuth()` in `src/worker/auth.ts` configures Better Auth with `emailAndPassword` only — no OAuth providers, no magic links, no passkeys. Every request is authorized by a session cookie, and `assertSameOrigin` in `src/worker/http.ts` actively rejects requests whose `Origin` header doesn't match `BETTER_AUTH_URL`, which is correct for a browser-only app but would reject any external script or integration by design. Authorization itself is coarse: three global roles (`owner`/`editor`/`viewer`, enforced by `requireOwner`/`requireEditor`/`requireMember` in `src/worker/auth.ts`) with no concept of a resource-scoped grant — there's no way to say "this connection can see page X but not page Y," which is exactly how Notion integrations work by default. Internal worker-to-Durable-Object calls don't have their own credential model either — they share one static secret, `x-notes-internal: env.BETTER_AUTH_SECRET`, checked identically in the document, workspace-events, archive, and cleanup Durable Objects.

The closest reachable target is a bearer-token Personal Access Token. The invite handlers in `src/worker/index.ts` and invite schema in `migrations/0001_initial.sql` provide a useful token-storage primitive — generate a high-entropy secret and retain only its hash — but not a lifecycle to copy. Invites are single-use, atomically consumed through `used_at`, and forced to expire after seven days. PATs are reusable credentials: they must have no consumption field, remain valid on every request until their configured expiration or revocation, and support replacement-before-revocation rotation. A compatible PAT table should store the token hash, owning user and workspace, capabilities, creation and expiration times, and nullable revocation metadata. Its creation flow should offer Notion's 7-, 30-, 90-, 180-day, and one-year expirations rather than imposing the invite lifetime.

With that separate lifecycle in place, a new auth middleware branch that accepts `Authorization: Bearer <token>` as an alternative to the session cookie (and a carve-out in `assertSameOrigin` for that path) is incremental work. Full OAuth — an authorization server, a page-picker consent screen, refresh-token rotation, and capability enforcement layered _under_ the existing role checks — is a genuinely new subsystem, and per-page resource grants would need a new table and a new authorization check inserted into every route, since today every check just asks "what's this user's global role."

### 4. Nothing leaves the building

Notion's webhook system attaches each subscription to a connection; it is not an unrestricted workspace event stream. Events are delivered only for resources that connection can access and only when its configured capabilities permit the event (comment events, for example, require comment-read capability). Delivery uses signed HTTP POSTs to a subscriber-controlled URL, with a one-time verification-token handshake and HMAC-SHA256 request signing.

At the API versions surveyed here, the supported event names are explicit rather than a resource-by-verb wildcard:

- Pages: `page.content_updated`, `page.created`, `page.deleted`, `page.locked`, `page.moved`, `page.properties_updated`, `page.undeleted`, and `page.unlocked`.
- Databases: `database.created`, `database.deleted`, `database.moved`, and `database.undeleted`. `database.content_updated` and `database.schema_updated` are the pre-`2025-09-03` forms and are deprecated in that version.
- Data sources, introduced for webhook API version `2025-09-03`: `data_source.content_updated`, `data_source.created`, `data_source.deleted`, `data_source.moved`, `data_source.schema_updated`, and `data_source.undeleted`.
- Comments: `comment.created`, `comment.updated`, and `comment.deleted`.
- File imports: `file_upload.complete` and `file_upload.upload_failed`.
- Views: `view.created`, `view.updated`, and `view.deleted`, available on API version `2025-09-03` and later. There is no `view.moved` event.

This app has no outbound HTTP delivery mechanism anywhere — no Cloudflare Queues binding, no webhook subscription table, no signing code, nothing (the full binding lists in `wrangler.jsonc` and `src/worker/env.ts` contain only `DB`, `BUCKET`, and the two Durable Object namespaces). What it does have is a well-built _internal_ precedent that's easy to mistake for a head start until you look closely at where it stops: the `WorkspaceEvents` Durable Object in `src/worker/workspace-events.ts` validates and fans out strictly typed `pages-upserted`, `pages-removed`, and `projection-updated` events whenever `sendWorkspaceEvent()` records a page mutation or a document finishes compacting. `broadcastWorkspaceEvent()` is genuinely solid pub/sub — but it only reaches WebSocket-connected browser tabs in that workspace. It cannot POST to an external URL, has no subscriber list beyond "whoever's currently connected," and the Durable Object is explicitly read-only from the client's side by design, since it exists purely to push, not to accept writes.

Turning this into real webhooks means building, from nothing: a subscription table (URL, secret, exact event-type filter, active/paused status), resource-access and capability checks, a delivery mechanism (most naturally Cloudflare Queues, which isn't a binding in this project today) with retry/backoff for failed deliveries, and HMAC signing on the outbound payload. `WorkspaceEvent` in `src/shared/types.ts` is a useful internal transport precedent, but its three coarse event types are not the public taxonomy above; an external adapter must deliberately map mutations onto the versioned webhook names and payloads.

## Follow-up: three ready areas and one compatibility limit

The three ready areas don't touch any of the four blockers above. Each is a thin translation layer over a route or index that already exists, callable today by whatever auth mechanism ends up fronting a new API surface. The Users API is close, but its remaining gaps depend on the auth adapter rather than response-envelope naming alone.

**Search API** (`POST /v1/search` in Notion's shape). The `GET /api/search` handler in `src/worker/index.ts` already queries the `page_search` FTS5 virtual table defined in `migrations/0001_initial.sql`, ranks by `bm25()`, and returns highlighted snippets — and it matches on **title and body text**, where Notion's own search API only matches page/data-source titles. A wrapper here is strictly a narrowing of what's already exposed, not a climb.

**Users API — compatibility-limited** (`GET /v1/users`, `/v1/users/{id}`, `/v1/users/me`). `GET /api/members` and `GET /api/me` provide useful source data, but they do not cover the Notion surface directly: there is no member-by-ID `GET` route, and `/api/me` returns the person authenticated by the browser session while Notion's `/v1/users/me` returns the identity associated with the authorization token. A real adapter therefore needs a workspace-scoped member lookup plus an explicit mapping from each PAT or OAuth token to the Notion user it represents (a person or a connection bot), including the appropriate capability-based field redaction. It must derive `type` and the corresponding `person` or `bot` object from that mapping rather than hard-coding `type: "person"`. Until blocker #3 supplies those token identities, a session-only adapter can expose member people but cannot claim compatible `/v1/users/{id}` or `/v1/users/me` behavior.

**Move Page** (`POST /v1/pages/{id}/move`). The `POST /api/pages/:id/move` handler in `src/worker/index.ts` already does this, and does slightly more than Notion's version: it accepts a target parent plus `beforeId`/`afterId` siblings and computes a new fractional-index position in the same call, with cycle prevention via a recursive CTE rather than requiring a separate reorder step.

**Pagination and error envelope.** Notion's list responses (`{object: "list", results, has_more, next_cursor}`) and error objects (`{object: "error", status, code, message}`) both have direct analogues already in production here. Cursor pagination exists today in the mention-inbox handler in `src/worker/index.ts` — an opaque `{firstSeenAt, pageId}` cursor with a `nextCursor` in the response. The typed `HttpError` model in `src/worker/http.ts`, with specific per-domain codes like `table_lease_lost`, `page_cycle`, and `archive_first`, is structurally the same idea as Notion's own per-domain codes (e.g. `select_required`). Standardizing on Notion's exact envelope shape, and a `Notion-Version`-style required header, for any new API surface is a naming exercise, not new engineering.
